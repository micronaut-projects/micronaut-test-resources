The Docker Compose module lets Micronaut Test Resources resolve supported missing properties from services declared in a local Compose file instead of starting a separate default provider container.
This support is opt-in and intended for development and test execution only.

dependency:micronaut-test-resources-compose[groupId="io.micronaut.testresources", scope="test"]

The Compose module exposes provider-owned Compose resolvers for the built-in container-backed Test Resources modules.
Containerless or delegating modules, such as H2, R2DBC pool, Oracle Test Pilot, and generic Testcontainers mappings, do not have independent Compose service matching.

Enable Compose support with the `test-resources.compose.enabled` property:

[configuration]
----
test-resources:
  compose:
    enabled: true
----

When enabled, Test Resources looks for `compose.yml`, `compose.yaml`, `docker-compose.yml`, or `docker-compose.yaml` in the working directory.
You can choose files and profiles explicitly:

[configuration]
----
test-resources:
  compose:
    enabled: true
    files:
      - compose.yml
      - compose.test.yml
    profiles:
      - dev
      - test
----

Compose matching is implemented by provider-owned resolvers.
The Compose module makes Compose resolvers visible for the supported database, messaging, storage, search, discovery, identity, and single-service provider modules.
Compose resolvers run before the matching default Testcontainers provider.
For supported modules, enabling Compose disables the original provider instance and uses the Compose-aware provider variant instead.
That variant first tries to resolve the missing property from Compose.
When a matching Compose service is found, the Compose value is returned and no separate default provider container is started.
When no Compose service matches, the same provider falls back to the existing Testcontainers startup behavior.

This means inference still works through the existing provider module.
For example, if inference determines that `datasources.default.url` is missing and the PostgreSQL provider is available, the PostgreSQL Compose-aware provider tries Compose first.
If exactly one matching Compose service can provide the datasource, Test Resources uses it.
If Compose is disabled or no unambiguous PostgreSQL service is available, the normal PostgreSQL Test Resources container path is used.
If multiple Compose services could satisfy the same property, Test Resources logs the ambiguity and falls back instead of choosing one arbitrarily.

.PostgreSQL and Redis
[source,yaml]
----
services:
  db:
    image: postgres:17
    ports:
      - "5432"
    environment:
      POSTGRES_USER: demo
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: demo
    labels:
      io.micronaut.test-resources.service: postgres
      io.micronaut.test-resources.datasource: default
  cache:
    image: redis:7
    ports:
      - "6379"
    labels:
      io.micronaut.test-resources.service: redis
----

With this Compose file, Test Resources can provide `datasources.default.url`, `datasources.default.username`, `datasources.default.password`, `datasources.default.driver-class-name`, and `redis.uri`.

.RabbitMQ
[source,yaml]
----
services:
  broker:
    image: rabbitmq:4
    ports:
      - "5672"
    environment:
      RABBITMQ_DEFAULT_USER: demo
      RABBITMQ_DEFAULT_PASS: secret
    labels:
      io.micronaut.test-resources.service: rabbitmq
----

With this Compose service, Test Resources can provide `rabbitmq.uri`, `rabbitmq.username`, and `rabbitmq.password`.

Use labels when automatic image and port matching would be ambiguous:

[source,yaml]
----
labels:
  io.micronaut.test-resources.service: postgres
  io.micronaut.test-resources.datasource: inventory
----

The `io.micronaut.test-resources.service` label accepts the provider service name, such as `postgres`, `mysql`, `mariadb`, `mssql`, `oracle`, `redis`, `rabbitmq`, `mongodb`, `kafka`, `localstack`, `minio`, `opensearch`, `solr`, `keycloak`, or `wiremock`.
Use credential labels such as `io.micronaut.test-resources.username`, `io.micronaut.test-resources.password`, and `io.micronaut.test-resources.database` when the Compose image does not use the standard environment variables for that service.

You can exclude a Compose service from Test Resources matching:

[source,yaml]
----
labels:
  io.micronaut.test-resources.ignore: "true"
----

Additional Compose lifecycle options are available under `test-resources.compose`:

[configuration]
----
test-resources:
  compose:
    enabled: true
    project-name: inventory-tests
    start: true
    stop-managed: true
    startup-timeout: 60s
----

`start` controls whether Test Resources runs `docker compose up -d`.
When `start` is `false`, Test Resources only inspects already-running services.
When `stop-managed` is `true`, shutdown stops only services that Test Resources started for the current Compose project.
Services that were already running before Test Resources started are reused and left running.

The build plugins still manage the lifecycle of the Test Resources server.
Compose lifecycle is tied to that server process, so keep-alive settings affect how long Test Resources keeps ownership of Compose services it started:

[cols="1,1,1,1", options="header"]
|===
| Test Resources server mode
| `compose.start`
| `compose.stop-managed`
| Compose lifecycle result

| Per-build server, no keep-alive
| `true`
| `true`
| Test Resources starts missing Compose services for the build and stops only those services when the server shuts down. Services that were already running are left running.

| Keep-alive/shared server
| `true`
| `true`
| Test Resources starts missing Compose services once and keeps them available while the server remains alive. They are stopped only when that server process actually shuts down.

| Any server mode
| `true`
| `false`
| Test Resources may start Compose services, but it does not stop them. Lifecycle cleanup is left to the user or CI job.

| Any server mode
| `false`
| Any value
| Test Resources only inspects already-running Compose services. It does not start or stop Compose services.
|===

The Compose resolver requires Docker Compose V2 through the Docker CLI.
If Docker, Compose V2, a Compose file, a published host port, or an unambiguous mapping is not available, diagnostics are written to the logs and Test Resources falls back to the normal provider when possible.
Diagnostic output redacts credential-like values such as passwords, secrets, tokens, keys, and credentials.

Enabling Compose can run local images and use mounts declared by the Compose file.
Only enable it for trusted development and test Compose files.
