The Docker Compose module lets Micronaut Test Resources resolve supported missing properties from services declared in a Compose file.
This support is opt-in and intended for development and test execution only.

dependency:micronaut-test-resources-compose[groupId="io.micronaut.testresources", scope="test"]

Add the normal provider module for the service you use, then add the Compose module.
For example, a PostgreSQL application still needs the PostgreSQL Test Resources provider on the Test Resources server classpath, and Redis support still needs the Redis provider.
The Compose module acts as an overlay that runs before the default providers.
When it finds one unambiguous supported Compose service, it resolves the missing property from that service.
When it cannot safely resolve the property, the existing provider starts the normal Testcontainers resource.

The Compose module does not replace provider modules.
It provides the shared Compose lifecycle and lookup support used by Compose-aware provider resolvers.
For example:

* PostgreSQL JDBC needs `micronaut-test-resources-jdbc-postgresql` and `micronaut-test-resources-compose`.
* Redis needs `micronaut-test-resources-redis` and `micronaut-test-resources-compose`.
* RabbitMQ needs `micronaut-test-resources-rabbitmq` and `micronaut-test-resources-compose`.
* Kafka, MongoDB, and LocalStack follow the same pattern: add the normal provider module plus `micronaut-test-resources-compose`.

Enable Compose support with the `test-resources.compose.enabled` property:

[configuration]
----
test-resources:
  compose:
    enabled: true
----

When enabled, Test Resources checks for `compose.yml`, `compose.yaml`, `docker-compose.yml`, or `docker-compose.yaml` in the working directory.
You can choose files and profiles explicitly:

[configuration]
----
test-resources:
  compose:
    enabled: true
    files:
      - compose.yml
      - compose.test.yml
    profiles:
      - dev
      - test
----

Test Resources uses Testcontainers' Docker Compose support to start an isolated Compose environment.
Services are exposed through Testcontainers, so the Compose file does not need host-published `ports` for Test Resources to connect.
Test Resources does not adopt arbitrary Compose projects that are already running outside Testcontainers.
If you want to use a fully external Compose stack, keep supplying explicit Micronaut properties for that stack.

Compose resolution is attempted only for missing properties that the matching provider can normally supply.
A service is considered only when:

* Compose support is enabled.
* The service is not marked with `io.micronaut.test-resources.ignore=true`.
* The service matches a supported descriptor by explicit service label, image name, or exposed internal port.
* Exactly one candidate can satisfy the requested property.

If any of those checks fail, the Compose resolver returns no value and the normal provider fallback remains in control.
This keeps existing Test Resources behavior unchanged for applications that do not enable Compose, do not add the Compose module, or have an unsupported Compose service.

.PostgreSQL and Redis
[source,yaml]
----
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: demo
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: demo
  cache:
    image: redis:7
----

With this Compose file, Test Resources can provide `datasources.default.url`, `datasources.default.username`, `datasources.default.password`, `datasources.default.driver-class-name`, and `redis.uri`.
The PostgreSQL credentials use the standard environment variable names from the official PostgreSQL image; use explicit labels when a custom image uses different names.

Credential and database values are resolved in this order:

1. Explicit Micronaut labels on the Compose service.
2. Supported image-specific environment variables, such as `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` for the official PostgreSQL image.
3. Provider defaults where the matching Test Resources provider has a stable default.

Use labels when automatic image and port matching would be ambiguous:

[source,yaml]
----
labels:
  io.micronaut.test-resources.service: postgres
  io.micronaut.test-resources.datasource: inventory
----

The `io.micronaut.test-resources.service` label accepts the canonical service type or a supported alias.
The resolver also tries to match by image name and the service's exposed internal port, but explicit labels are preferred for custom images and multi-service Compose files.

Use credential labels when the Compose image does not use one of the supported standard environment variable names:

[source,yaml]
----
services:
  inventory-db:
    image: internal/postgres-dev:latest
    labels:
      io.micronaut.test-resources.service: postgres
      io.micronaut.test-resources.datasource: inventory
      io.micronaut.test-resources.username: inventory
      io.micronaut.test-resources.password: secret
      io.micronaut.test-resources.database: inventory
----

Use the ignore label for services that should not participate in Test Resources matching:

[source,yaml]
----
services:
  manually-configured-db:
    image: postgres:17
    labels:
      io.micronaut.test-resources.ignore: "true"
----

The supported service families use the following service-specific configuration sources:

[cols="1,2,2", options="header"]
|===
| Service family
| Standard Compose environment variables
| Defaults and notes

| PostgreSQL JDBC
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`
| These are the official PostgreSQL image variables. If they are absent, the provider falls back to its normal `test` user, password, and database defaults unless explicit labels override them.

| Redis
| None
| Only unauthenticated single-node Redis is mapped. If `REDIS_PASSWORD` or `io.micronaut.test-resources.password` is present, Compose resolution is skipped and the normal Redis provider remains the fallback.

| RabbitMQ
| `RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS`
| If they are absent, the provider uses RabbitMQ's `guest` user and password defaults unless explicit labels override them.

| Kafka and Redpanda
| None
| Compose supplies only the mapped bootstrap endpoint. Topic provisioning and credentials are not inferred from Compose in this module revision.

| MongoDB
| `MONGO_INITDB_DATABASE`
| The database name comes from the explicit database label, `MONGO_INITDB_DATABASE`, the named `mongodb.servers.*` entry, or the default `test` database. Username and password are not inferred in this module revision.

| LocalStack
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`
| If they are absent, the provider uses LocalStack-compatible defaults: access key `test`, secret key `test`, and region `us-east-1`. S3, DynamoDB, SQS, and SNS endpoint overrides come from the Compose service endpoint.

|===

Supported labels are:

[cols="1,1", options="header"]
|===
| Label
| Purpose

| `io.micronaut.test-resources.service`
| Selects the supported service type, such as `postgres`, `redis`, `rabbitmq`, `kafka`, `mongodb`, or `localstack`.

| `io.micronaut.test-resources.datasource`
| Selects the logical datasource name for database services. If omitted, an unambiguous database service maps to `default`.

| `io.micronaut.test-resources.username`
| Overrides the service username when the service family supports username resolution.

| `io.micronaut.test-resources.password`
| Overrides the service password when the service family supports password resolution.

| `io.micronaut.test-resources.database`
| Overrides the service database name when the service family supports database selection.

| `io.micronaut.test-resources.access-key`
| Overrides the access key for object-storage style services.

| `io.micronaut.test-resources.secret-key`
| Overrides the secret key for object-storage style services.

| `io.micronaut.test-resources.token`
| Reserved for provider mappings that support token-based service credentials.

| `io.micronaut.test-resources.realm`
| Reserved for provider mappings that support realm-based services.

| `io.micronaut.test-resources.client-id`
| Reserved for provider mappings that support client IDs.

| `io.micronaut.test-resources.client-secret`
| Reserved for provider mappings that support client secrets.

| `io.micronaut.test-resources.ignore`
| Excludes a service from Compose matching when set to `true`.
|===

Database values are read from explicit labels first, then from the common image-specific environment variables, and finally from the same defaults used by the matching Test Resources provider where possible.
Redis support resolves unauthenticated single-node `redis.uri`.
If Redis authentication is configured, the Compose resolver logs that it cannot safely map the URI and falls back to the normal Redis provider.
When more than one service could satisfy the same property, add `io.micronaut.test-resources.service` and the provider-specific selector label, such as `io.micronaut.test-resources.datasource`, to the intended service.

Additional Compose options are available under `test-resources.compose`:

[configuration]
----
test-resources:
  compose:
    enabled: true
    startup-timeout: 60s
    local-compose: false
    docker-image-name: docker
----

`startup-timeout` controls the Testcontainers wait timeout for exposed Compose services.
`local-compose` switches Testcontainers to host Docker Compose execution for teams that require host credential helpers or local Compose behavior.
When `local-compose` is `false`, Testcontainers uses its containerized Compose mode with the configured `docker-image-name`.

The build plugins still manage the lifecycle of the Test Resources server.
Compose services live for the same Test Resources scope that created them:

[cols="1,1", options="header"]
|===
| Test Resources event
| Compose lifecycle result

| Per-build server shutdown
| Testcontainers stops the Compose environment started for that server.

| Keep-alive/shared server
| Testcontainers-managed Compose services remain running until the shared Test Resources server or owning scope closes.

| Scope close
| Compose environments for that scope and child scopes are stopped.

| Server close all
| All Testcontainers-managed Compose environments are stopped.
|===

Diagnostics are written to the logs for matched, ignored, unmatched, and ambiguous services, Docker/Testcontainers startup failures, Compose file parsing problems, and missing local Compose support when `local-compose=true`.
Diagnostic output redacts credential-like values such as passwords, secrets, tokens, keys, and credentials.

Common troubleshooting checks:

* If Compose is not used, verify that `micronaut-test-resources-compose` and the normal provider module are both on the Test Resources server classpath.
* If no Compose file is found, set `test-resources.compose.files` or run the build from the directory that contains `compose.yml` or `docker-compose.yml`.
* If a service is unmatched, add `io.micronaut.test-resources.service` with the supported service type.
* If a service is ambiguous, add the provider selector label, such as `io.micronaut.test-resources.datasource`.
* If a credential is missing for a custom image, add the explicit username, password, database, token, or key label supported by the service family.
* If `local-compose=true` fails, verify that Docker Compose V2 is available to the build environment.

Enabling Compose can run local images and use mounts declared by the Compose file.
Only enable it for trusted development and test Compose files.
